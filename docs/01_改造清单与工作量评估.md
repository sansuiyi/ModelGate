# ModelGate 技术栈改造清单与工作量评估

> 目标：**业务逻辑尽量不改，技术含金量明显提升**。
> 改造策略：把"FastAPI + SQLite + Python 单进程原型"升级为 **"Java 21 + Spring Boot 3 企业级微服务底座"**，并引入 MySQL / Redis / Kafka / Spring Cloud Gateway / 可观测性等生产级组件。核心的路由决策、合约约束过滤、分类启发式等纯业务逻辑 1:1 平移，接口契约保持不变，前端无需改动。

---

## 二、后端逐模块改造清单

### 2.1 配置层：`config.py` → Spring 配置

| 现有项 | 目标实现 |
|---|---|
| `OPENROUTER_API_KEY` | `application.yml` + `OPENROUTER_API_KEY` 环境变量 + `@ConfigurationProperties(OpenRouterProperties)` |
| `OPENROUTER_BASE_URL` | `OpenRouterProperties.baseUrl` |
| `EXTRACTION_MODEL = "openai/gpt-5.4"` | `OpenRouterProperties.extractionModel` |
| `CLASSIFIER_GGUF_PATH` | `ClassifierProperties.ggufPath` |
| `CLASSIFIER_N_CTX` / `N_GPU_LAYERS` | `ClassifierProperties.nCtx` / `nGpuLayers` |
| `DB_PATH`（SQLite 路径） | **移除**，改由 DataSource + JPA 管理 MySQL |
| `CONTRACTS_DIR` / `SAMPLE_CONTRACTS_DIR` / `FALLBACK_PROFILES_DIR` | 文件路径配置，保留（合同文件、回退 profile 文件仍可读文件系统，或用 MySQL 存大文本） |

**工作量**：0.5 人天。

### 2.2 持久层：`database.py` → JPA Repository + Flyway

现有 `database.py` 手写了 3 张表与全部原生 SQL：

| 现有表 | Spring 实现 |
|---|---|
| `customers`（`customer_id` PK，`data` JSON 全量存客户档案，`created_at`） | `CustomerEntity` + `CustomerRepository`（`save/delete/findById`） |
| `request_logs`（含 input/output tokens、ttft、candidates 等 17 列） | `RequestLogEntity` + `RequestLogRepository`（分页查询） |
| `global_models`（`model_name` PK，`custom_config` JSON 存模型元数据） | `GlobalModelEntity` + `GlobalModelRepository` |

> **关键改造点**：现在 `customers.data` 和 `global_models.custom_config` 是**整段 JSON 字符串**存储，业务读取时再反序列化。建议升级为**规范化字段 + JSON 类型列**（MySQL 的 `JSON` 类型 + `@JdbcTypeCode(SqlTypes.JSON)` 或 MapStruct），既保留灵活性，又让 SQL 可查询、可索引。

**数据库迁移**：引入 **Flyway**，在 `db/migration/V1__init.sql` 建表。旧 SQLite 数据可写一个一次性脚本导出为 JSON 再导入 MySQL。

**统计逻辑**：`get_customer_stats()` / `get_global_stats()` 目前是全表读入内存再聚合（p95、p99、分布、按小时统计）。改造建议：
- 短周期统计（当日/小时）：SQL 聚合（`GROUP BY HOUR`）实现；
- 长期/大数据量统计：**从 Kafka 消费请求日志写入 ClickHouse 或 ES**（可选加分项），或先保留 MySQL 聚合，配索引。

**工作量**：3 人天（含实体、仓库、Flyway 脚本、SQLite→MySQL 数据迁移脚本）。

### 2.3 模型层：`models.py`（Pydantic）→ DTO + 领域对象

| Pydantic 模型 | Java 实现 |
|---|---|
| `CustomerConstraints` | `CustomerConstraints`（`region`, `privacyTier`, `forbiddenProviders`, `allowedProviders`） |
| `CustomerPerformance` | `CustomerPerformance`（`latencyTargetMs`, `costSensitivity`） |
| `CustomerProfile` | `CustomerProfile` 领域对象 + DTO（`CustomerProfileResponse`） |
| `RoutingDecision` | `RoutingDecision` 领域对象 |
| `ChatCompletionRequest` | `ChatCompletionRequestDto` |
| `CustomerStats` | `CustomerStatsResponse` |
| `RequestLogEntry` | `RequestLogEntry` + `RequestLogResponse` |

用 **Java Record + validation (jakarta.validation)** 替代 Pydantic 的字段校验，`@Valid` 做请求校验，`ObjectMapper` 做 JSON 序列化。

**工作量**：2 人天。

### 2.4 服务层

#### 2.4.1 `provider_registry.py` → `ModelCatalogService`

| 现有函数 | Spring 实现 |
|---|---|
| `DEFAULT_MODELS` 常量 | `application.yml` 配置或数据库初始化种子数据 |
| `get_active_catalog()` | `ModelCatalogService.getActiveCatalog()` —— 优先查 DB，空则回退配置 |
| `get_model_info(name)` | `ModelCatalogService.getModelInfo(name)` |
| `get_openrouter_id(name)` | `ModelCatalogService.getOpenRouterId(name)` |
| `get_models_for_tier(tier)` | `ModelCatalogService.getModelsForTier(tier)` |
| `estimate_cost(...)` | `ModelCatalogService.estimateCost(...)` |
| `get_all_providers()` / `get_all_model_names()` | `ModelCatalogService.getProviders()` / `getModelNames()` |

> **Redis 缓存**：`getActiveCatalog()` 是高频读取点（每次请求都查），可加 `@Cacheable("modelCatalog")`，在模型增删改时 `@CacheEvict`。客户档案 `getCustomer(id)` 也可加缓存。

**工作量**：1.5 人天（含缓存）。

#### 2.4.2 `classifier.py` → `PromptClassifier`

| 现有函数 | Spring 实现 |
|---|---|
| `load_classifier()` | `ClassifierInitializer`（启动时加载）或 `@PostConstruct` |
| `classify_prompt(prompt)` | `PromptClassifier.classify(prompt)` —— 短 prompt 快速判 simple，再走模型/启发式 |
| `_arch_router_classify(prompt)` | 调用本地推理服务（见下） |
| `heuristic_classify(prompt)` | `HeuristicClassifier.classify(prompt)` —— 关键词词表 + 打分逻辑平移 |
| `ROUTE_POLICIES` | 常量或配置 |

> **本地 GGUF 推理的 Java 化**：Python 的 `llama-cpp-python` 在 Java 里没有等价的成熟库。三种方案（推荐按顺序）：
> 1. **独立推理服务**：把 GGUF 推理封装成一个独立 Python 服务（gRPC/HTTP），Spring 通过 HTTP 调用。**最省事、含金量不减**（微服务化）。
> 2. **ONNX Runtime**：把路由分类模型导出为 ONNX，用 `onnxruntime-java` 推理（无需 GPU 也能跑，生产友好）。
> 3. **llama.cpp JNI**：用 llama.cpp 的 Java 绑定（较 hacky，不推荐）。
>
> 分类逻辑本身（短 prompt 快速通道 + 模型结果 + 启发式回退）保持与源一致。

**工作量**：启发式平移 0.5 人天；GGUF 推理服务方案 2 人天。

#### 2.4.3 `router_engine.py` → `RoutingEngineService`

这是**最核心、业务含金量最高**的模块，必须 1:1 平移：

| 现有逻辑 | Java 平移 |
|---|---|
| `route(profile, prompt, tier_override)` | `RoutingEngineService.route(CustomerProfile, String, String)` |
| 候选 = `routing_preferences[tier]`，空则默认候选 | 平移 |
| 逐候选淘汰：disabled / 不在 registry / forbidden provider / 不在 allowed / region 不支持 | 平移（`EliminationReason` 枚举） |
| 无候选 → 层级升级 `TIER_ESCALATION` | 平移 |
| 再回退 → 全目录找第一个 policy 通过者 | 平移 |
| 兜底 `gpt-4o-mini` | 平移（配置化） |
| `_score_and_select()` 目标加权评分（low_latency/low_cost/high_quality + 延迟达标 + 成本敏感） | 平移（`RoutingScorer`） |
| `_passes_policy()` | 平移 |
| 生成 `reason` 文本 | 平移（模板） |

**工作量**：2 人天。

#### 2.4.4 `extractor.py` → `ContractExtractionService`

| 现有函数 | Spring 实现 |
|---|---|
| `EXTRACTION_PROMPT` 模板 | 放 resources 下的 `.txt` 模板或常量 |
| `extract_profile(customer_name, contract_text, custom_instructions)` | `ContractExtractionService.extractProfile(...)` |
| 调用 OpenRouter `/chat/completions`（httpx） | **Spring AI `OpenAiChatClient`**（OpenAI 兼容协议）或 RestClient |
| 解析 JSON、去 markdown 代码块、构造 `CustomerProfile` | 平移（Jackson） |
| 失败回退 `_load_fallback()`（读 `fallback_profiles/*.json`） | 平移（Resource + ObjectMapper） |

> **Spring AI 的价值**：统一管理 chat client、支持重试、可观察性，替代手写 `httpx` + 手动错误处理，明显提升含金量。

**工作量**：2 人天。

### 2.5 路由层（Controller）：`routers/*.py` → Spring MVC

| FastAPI Router | 端点 | Spring Controller |
|---|---|---|
| `customers.py` | `GET/POST /customers`、`GET/PUT/DELETE /customers/{id}` | `CustomerController` |
| `extraction.py` | `POST /extract`、`POST /extract/upload` | `ExtractionController` |
| `models.py` | `GET/POST /models`、`PUT/DELETE /models/{name}`、`GET /models/openrouter/catalog` | `ModelController` |
| `logs.py` | `GET /logs`、`GET /logs/{id}`、`GET /stats`、`GET /stats/{id}` | `LogController` |
| `proxy.py` | `GET /{customer_id}/v1/models`、`POST /{customer_id}/v1/chat/completions` | `ProxyController` |

> **proxy.py 是核心**：`chat_completions` 要把 `X-Routing-Decision`、`X-Model-Used`、`X-Latency-Ms`、`X-TTFT-Ms`、`X-Classify-Ms`、`X-Cost` 等响应头原样返回（前端 `api.ts` 依赖这些 header），且要把 OpenAI 响应体透传。改造时**务必保持这些 header 与响应体结构完全一致**。

**工作量**：2 人天。

### 2.6 应用入口：`main.py` → Spring Boot 启动类

| FastAPI | Spring |
|---|---|
| lifespan：`init_db()` + `load_classifier()` | `ApplicationRunner` / `@EventListener(ApplicationReadyEvent)` 调 `DbInitializer` + `ClassifierInitializer` |
| CORS 中间件 | `WebMvcConfigurer` 配 CORS |
| 挂载 router | `@RestController` 自动装配 |

**工作量**：0.5 人天。

## 三、新增生产级组件（含金量提升点）

### 3.1 Redis（缓存层）
- 缓存：`modelCatalog`（模型目录）、`customerProfile:{id}`（客户档案）、`routingDecision:{hash}`（相同 prompt 决策缓存，可选）。
- 通过 `spring-boot-starter-data-redis` + `@Cacheable` 实现，模型/客户变更时失效。
- **工作量**：1 人天。

### 3.2 Kafka（消息与异步）
场景与设计：
| Topic | 生产者 | 消费者 | 用途 |
|---|---|---|---|
| `request-log` | ProxyController | 日志服务 / ES / 报表 | 异步化请求日志落库，主流程不被日志阻塞 |
| `routing-decision` | RoutingEngine | 监控 / 推荐 | 决策事件流，便于复盘与可视化 |
| `contract-extraction` | ExtractionController | 抽取服务 | 大合同文本异步抽取，避免请求长时间阻塞 |

主流程 `chat/completions` 保持同步，但**日志与统计**全部走 Kafka 异步，提升吞吐与解耦度。
- **工作量**：2 人天。

### 3.3 Spring Cloud Gateway（网关，可选但推荐）
- 作为统一入口，做路由、限流（Redis RateLimiter）、鉴权、`X-Routing-Decision` header 透传。
- 若暂时不需要多服务拆分，可先不引入，直接保留 `ProxyController`。
- **工作量**：1.5 人天（引入时）。

### 3.4 Spring Security + JWT
- 给 `/customers`、`/models`、`/extract` 等管理接口加鉴权；`/v1/{customer_id}/...` 走客户 API Key 或 JWT。
- **工作量**：1.5 人天。

### 3.5 可观测性（Micrometer + Prometheus + Grafana）
- 暴露 `/actuator/prometheus`，采集：请求 QPS、延迟分位、路由决策分布、模型成本、错误率。
- 与现有 Dashboard 的监控诉求契合。
- **工作量**：1 人天。

### 3.6 Spring AI
- 统一管理 OpenRouter 的 chat 调用（合同抽取），支持重试、log 记录。
- **工作量**：0.5 人天（含在 extractor 改造里）。

### 5.4 用 LLM 辅助改造的工作量评估（新增）

> 前置说明：下面是在 **"人工为主、LLM 编码助手为辅"** 与 **"LLM 主力生成、人工审查联调"** 两种模式下的评估。核心耗时仍集中在：Spring 工程初始化、跨文件上下文理解、契约保真、联调与测试——LLM 显著压缩的是"脚手架 + 逐模块翻译 + 样板代码"部分。

#### 5.4.1 不同模式对比

| 模式 | 说明 | P0+P1+P2（最小可用） | +P3（生产级） | +P4（全量） |
|---|---|---|---|---|
| A. 纯人工 | 传统手写 | 14.5 人天 | 20.5 人天 | 24 人天 |
| **B. 人工主导 + LLM 辅助** | 工程师搭骨架、定契约，LLM 生成模块/模板，人工审查合入 | **约 8–10 人天** | **约 12–14 人天** | **约 15–17 人天** |
| C. LLM 主导 + 人工审查 | LLM 批量生成大部分代码，工程师做架构把关与联调收尾 | 约 6–8 人天 | 约 9–12 人天 | 约 12–15 人天 |

> 建议采用 **模式 B（人工主导 + LLM 辅助）**：既能明显提速，又能守住契约与架构质量，避免 LLM 主导下越权改接口、引入非标准依赖、跳过验证等风险。

#### 5.4.2 关键耗时分布（模式 B，单位：人天）

| 阶段 | 纯人工 | LLM 辅助 | 说明（LLM 加速点） |
|---|---|---|---|
| 工程骨架 / pom / 配置 / 启动类 | 1.0 | 0.3 | 一次性让 LLM 生成可编译骨架 |
| 实体 + JPA + Flyway + 数据迁移 | 3.0 | 1.5 | LLM 批量产出 Entity/Repository/SQL，人工核对字段映射 |
| DTO / 领域对象 / 校验 | 2.0 | 0.8 | 样板代码为主，LLM 高收益 |
| 服务层平移（路由/分类/抽取/目录） | 5.5 | 3.0 | 将源 `.py` 源码喂给 LLM 做跨语言 1:1 平移，人工审查业务等价 |
| Controller + Proxy 契约保真 | 2.0 | 1.2 | **人工重点把关** 7 个响应头与响应体结构 |
| Redis / Kafka / 安全 / 监控（P3） | 6.0 | 3.5 | LLM 生成配置与样板，人工做集成验证 |
| 网关 / 推理服务（P4） | 3.5 | 2.5 | 需人工做架构决策 |
| 测试 / 联调 / 部署 / 文档 | 4.0 | 2.5 | 单元测试可由 LLM 生成，联调需人工 |
| **合计** | **14.5 / 20.5 / 24** | **8–10 / 12–14 / 15–17** | — |

#### 5.4.3 LLM 改造加速的适用条件与注意点

- **加速最明显**：Python→Java 的机械翻译、Entity/DTO/Repository 样板、Flyway SQL、application.yml、单元测试骨架。
- **必须人工把关（不建议交给 LLM 独断）**：API 契约保真（`X-*` 响应头、OpenAI 响应体）、路由决策算法等价性、安全配置、事务边界。
- **建议**：把三份 docs 文档（本清单 / 骨架 / 中文化）作为 LLM 的输入上下文，能显著降低"从零理解仓库"的 token 成本并提高一次性正确率。
- **模型选择建议**（针对"快速 + 代码质量好"，详见对话回复）：优先 **GLM-5.2**（长程重构/跨语言改造/工程规范遵循最优，开源 SOTA），`deepseek-v4-pro` 作为复杂点复核或兜底，`deepseek-v4-flash` 适合简单子任务批量处理（不建议做复杂长链重构的主力）。

## 六、风险与建议

### 6.1 主要风险
| 风险 | 等级 | 缓解 |
|---|---|---|
| Proxy 的响应头/响应体保真度 | 高 | 用契约测试（spring-cloud-contract）锁定 header 与 JSON 结构 |
| SQLite 单文件 → MySQL 的并发/事务行为差异 | 中 | Flyway 迁移 + 迁移测试 |
| GGUF 本地推理的 Java 化 | 中 | 优先走独立推理服务，避免与业务耦合 |
| 统计数据由内存聚合改 SQL/流式聚合 | 中 | 先保功能等价，再做流式升级 |

### 6.2 建议顺序
1. 先做 **P0 + P2**（骨架 + 数据迁移），跑通 `/health` 与 `/v1/...` 主链路。
2. 再做 **P1**（服务层平移），跑通全部分类/路由/抽取。
3. 再上 **P3**（Redis/Kafka/安全/监控），逐步增强。
4. 最后视需要做 **P4**（网关、推理服务）。
